# 目标追踪新功能

给原入侵检测工程补上**帧间关联**这一层。原检测链每帧给一堆互不相关的框，
无法回答"这是不是同一个人"，因此算不出方向、速度、计数。

## 文件

| 文件 | 作用 |
|---|---|
| `target_tracker.py` | 跟踪器本体。纯 numpy，无 cv2 依赖，可离线测 |
| `strip_merge.py` | 细边合并。帧差法的补救措施；用 `bg` 检测后基本不需要 |
| `bg_detector.py` | **PS 端背景模型检测器**，解决"远处不识别"和"只抓一部分" |
| `tracker_server.py` | 演示服务：实时画面 + 每个目标的方向/速度表 |
| `test_target_tracker.py` | 跟踪器测试（28 项） |
| `test_strip_merge.py` | 细边合并测试（15 项） |
| `test_bg_detector.py` | 背景模型测试（19 项） |
| `eval_strip_merge.py` | 用已知真值量化合并效果，输出召回率/精确率 |
| `eval_detection_modes.py` | 尺寸×速度扫描，对比帧差与各种背景模型配置 |
| `eval_bg_configs.py` | 背景模型形态学参数选型 |
| `eval_scene_change.py` | 场景变化后背景收敛速度（曾用它定位舍入死区 bug） |
| `recon_detections.py` | 侦察脚本：打印检测器实际输出（改断言前先看真实数据） |

## 检测方式：默认用队友的链路

**默认 `--detector pl`，且 `--merge-gap 0`** —— 即**完全使用交付包原有的帧差判定链**，
本目录的代码不在其上做任何框的合并或改写。队友那套判定是已经调好的折中方案，
之前我把检测层越改越复杂，效果反而更差，所以恢复原状，**新功能只做加法**。

| | `--detector pl`（**默认**） | `--detector bg`（可选，对比用） |
|---|---|---|
| 算法 | 交付包的 PL 帧差链路 | PS 运行平均背景模型 |
| 框的判定 | **队友原样** | 本目录重写 |
| 召回 / 精确 | 0.027 / 0.018 | 0.746 / 0.952 |
| 一个物体几个框 | 恒定 2 个（前沿/后沿） | 约 1.3 个 |

`bg` 模式保留下来是因为它在某些场景确实更灵敏，但它**不是默认**，
也不影响 `pl` 模式的行为。

> `--merge-gap 62` 会在 `pl` 模式下把物体的两条边缘细条并成一个框。
> 这是**本目录新增的改动**，默认关闭；需要时再开。

## 轨迹平滑

原来的轨迹是「逐帧位置连成的折线」—— 检测框每帧抖一两像素，画出来是**锯齿**。
现在两层处理，各解决一半：

**1. 消抖（`--trail-min-move`，默认 3px）**：目标移动不足 3px 就**不记录新点**。
静止目标不再画出一团抖动，点数量也大幅减少。

**2. 平滑曲线**：记录到的点仍由直线连接，稀疏时棱角明显。
先用**居中滑动平均**（`--trail-smooth`，默认窗口 7）整理间距，
再用 **Catmull-Rom 样条**拟合 —— 样条**穿过每一个记录点**，
所以画出来的路径仍然走目标真实走过的地方，只是进出每个点时是圆润的。

实测效果（慢速移动 + ±8px 抖动）：

| | 平均转角 | 最大偏离记录点 |
|---|---|---|
| 原始折线 | 162.5° | — |
| 只消抖 | 162.5° | — |
| **消抖 + 平滑** | **9.4°** | **4.0px** |

> **两层各管一半，而且有各自有效的条件**：
> 抖动幅度 **小于** `min_move` 时消抖非常有效（实测 60 点 → 3 点，减少 95%）；
> 抖动幅度 **大于** `min_move` 时消抖无能为力，那时靠平滑
> （实测快移场景从 162° 降到 3.7°）。

**性能**：拟合 40 点约 0.42ms、120 点约 1.16ms，而 16.7 FPS 的帧预算是 60ms
（占 0.7%~2%）。而且**只在记录到新点时才重建**，渲染层只读缓存好的路径，
所以帧的延迟完全不受影响 —— 不需要独立线程。

### 轨迹保留多久

| 参数 | 默认 | 含义 |
|---|---|---|
| `--trail-min-move` | **3** | 消抖：目标移动多少**像素**才记录新点 |
| `--trail-smooth` | **7** | 平滑窗口 |
| `--trail-seconds` | 6 | 轨迹显示多少**秒**的历史 |
| `--trail-linger` | **1** | 目标消失后轨迹**继续显示**多少秒 |

> `--trail-min-move` 是**距离不是时间**。调大它会让轨迹「一段一段跳着长」，
> 看起来与绿框不连贯 —— 实测调到 3px 后，记录点从 25 增到 44，
> 而且**曲线反而更贴合实际路线**（最大偏离 4.00px → 2.15px），
> 因为多出来的点都是真实位置，样条能「切角」的余地更小。

### 网页上可调（不用 SSH）

页面底部有 4 个滑块，**拖动即生效**：

| 滑块 | 范围 | 注意 |
|---|---|---|
| 消抖距离 | 0–20 px | 调大会让轨迹一段段跳着长 |
| 平滑窗口 | 1–15 | 偶数会自动降为奇数 |
| 历史长度 | 1–20 s | **调大不会找回已丢弃的旧点**，要等新轨迹累积 |
| 消失后滞留 | 0–5 s | 0 = 目标消失即清除 |

- `GET /trail` → `{settings, default, limits, stats}`
- `POST /trail` 例如 `{"seconds":10,"linger":2}` → 只改传了的字段；
  超范围**裁剪**、偶数平滑窗口**降为奇数**、非法值返回 **400**

> 网页上的调整**只在本次运行有效**，服务重启后回到命令行/环境变量的默认值。

**为什么是秒而不是点数**：原来用 `max_points`（点数）限制，
导致**轨迹时长随目标速度变化** —— 同一个设置下快目标约 7 秒、慢目标超过 20 秒。
改成按时间后，不论快慢都是设定值。

**为什么需要滞留期**：跟踪器在约 0.8 秒没有匹配后销毁轨迹，轨迹也跟着立刻消失。
所以「挥手到一半停下」时轨迹会突然不见 —— 你察觉到的多半是这个，
而不是轨迹本身太短。加上 `linger` 后轨迹会先停留再消失。

**渐隐**：轨迹沿长度从暗到亮绘制，一眼能看出运动方向。

> 轨迹显示与跟踪器内部的 `history` **是分开的**：`history` 供速度/方向/越线计数使用，
> 不能受消抖影响，否则速度估计会有偏。

## 越线计数

默认在画面**正中竖一条量线**，物体从左往右穿过计 `L>R`，反之为 `R>L`，
计数**实时显示在画面右上角**，网页上也同步显示，并有「清零计数」按钮。

在网页上可直接拖动**量线两端的圆点**改变位置/角度，或**拖线本身**整体平移。

判据上用了几道防线，避免重复计数：

- **停滞带（deadband，默认 4px）**：目标停在线上来回抖时，不改变「已记录的哪一侧」
- **只在画出的线段内计数**：越过线的延长线（线段之外）不算
- **首帧只定侧不计数**：目标可能一开始就出现在任意一侧
- **丢失后重现不算穿越**：轨迹消失会清除其状态
- **两条边去重**（详见下）

### 为什么需要去重

交付包的帧差链路把**一个运动物体报成两个目标**（前沿 + 后沿，因为在做帧间差），
跟踪器给它们**不同的 id**，于是两者都会过线一次 —— **一个人会被计两次**。

计数器的处理：**不同轨迹**在 `dedup_seconds`（默认 0.8s）内、
相距 `dedup_distance`（默认 45px）以内、**同方向**过线 → 判定为同一物体的两条边，只计一次。
**同一条轨迹**反复过线**永不抑制**（那是真实的往返运动）。

把 `dedup_distance` 设为 0 可关闭去重。

### 接口

- `GET /line` → `{enabled, line, default, width, height, dedup_seconds, dedup_distance}`
- `POST /line` body `{"line":[x1,y1,x2,y2]}` → 会裁剪到画面内、拒绝零长度线；
  **改线会清零计数**（旧计数不能归到新线）
- `GET /crossings` → `{labels, counts, total, recent:[…]}`，`recent` 是最近几次穿越的记录
- `POST /crossings/reset` → 清零
- 启动参数：`--line 60,180,260,180`，`--line none` 关闭计数

## 网页上调整警戒区

打开页面后**在画面上直接拖动黄色方框**即可移动警戒区，拖四个角可改大小。
改动实时生效（报警判定和画面同步更新），点「保存警戒区」写入服务端。

- `GET /zone` → `{zone, default, width, height, min_size}`
- `POST /zone` body `{"zone":[x,y,w,h]}`。
  服务端会**裁剪**到画面内、把**反向拖拽**（负的宽高）归一化、
  把过小的区域放大到 8×8，非法输入返回 400
- 启动时也可指定：`--zone 40,30,120,100`

## `bg_detector` 的两个关键设计点

**背景是 float32，不是 uint8。** uint8 的表达力不足以做慢速更新：
更新量 `rate × diff` 会被 `addWeighted` 舍入成 0，速率 0.008 时 diff 低于约 62
就永久停止更新，而阈值是 30 —— 于是产生永久误报。实测数据见
`eval_scene_change.py`。

**条件更新。** 前景像素只以 `alpha_foreground` 的慢速率更新背景，
背景因此始终保持"空场景"估计，物体走过之后**不留残影**。

## 已知局限

- **摄像头必须固定。** 一晃动整幅画面都成了前景（帧差法同样如此）。移动后约 13 秒恢复。
- **完全静止的物体约 9 秒后被吸收**。`--bg-alpha-fg` 可调（更小=保持更久）。
- **启动时画面必须是空的**，前 8 帧入镜的东西会被学进背景。
- `strip_merge` 是启发式：**身高相近、并排、间距小于 `--merge-gap` 的两人会被合并成一个框**。
- 速度单位是 **px/s，未做相机标定**，不能换算成 m/s。
- 角度约定 `0°=右`、`90°=上`（图像 y 向下，已取反）。
