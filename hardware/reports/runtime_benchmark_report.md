## 4. 正式 PYNQ 对比口径

- 在 PYNQ-Z2 PS 上运行 OpenCV 和真实 PL 两个后端。
- 两端使用同一个预载内存帧列表；采集、磁盘读取、显示和 JPEG 编码不计时。
- 每个后端先预热 20 帧，再测固定 200 帧序列；每轮持续至少 5 秒，共 3 轮。
- 奇偶轮交换后端先后次序，降低温度和系统负载随时间变化造成的偏差。
- OpenCV 固定为 1 线程；记录 Python 进程单核口径、总 CPU 容量口径及系统 CPU。
- 最终 PL 驱动使用输入非缓存、输出可缓存的非对称 DMA 缓冲区，输入/输出通道由 `cv2.mixChannels` 搬运，并在 DMA 轮询时休眠 100 us。
- 两端复用相同的 PS 后处理、轮廓、合框和报警代码。
- 保存原始 CSV、JSON、bitstream SHA-256 和 Markdown 报告。

执行器：`software/deploy/pynq_compare_motion.py`。

## 5. 正式 PYNQ 结果

| 指标 | OpenCV 纯软件 | 优化 PL + 相同 PS 后处理 | PL 相对结果 |
|---|---:|---:|---:|
| 平均 FPS | 48.40 | 50.18 | 1.0367×（+3.67%） |
| FPS 标准差 | 0.35 | 0.37 | 三轮均稳定 |
| P50 延迟 | 20.585 ms | 19.874 ms | -0.711 ms |
| P95 延迟 | 20.770 ms | 20.019 ms | -0.751 ms |
| 进程 CPU/单核口径 | 99.98% | 96.25% | -3.73 个百分点 |
| 进程 CPU/总容量 | 49.99% | 48.13% | -1.87 个百分点 |
| 系统 CPU | 50.13% | 48.37% | -1.76 个百分点 |

| 一致性指标 | 正式结果 | 验收线 | 判定 |
|---|---:|---:|---|
| 掩码像素一致率 | 0.999975 | ≥0.95 | 通过 |
| 掩码平均 IoU | 0.998298 | ≥0.85 | 通过 |
| 目标数量一致率 | 1.000000 | ≥0.90 | 通过 |
| bbox 平均匹配 IoU | 1.000000 | ≥0.70 | 通过 |
| 报警一致率 | 1.000000 | ≥0.95 | 通过 |

优化前同一块优化 bitstream 配合原 Python I/O 路径仅为 20.25 FPS、P50 49.254 ms、单核 CPU 100.03%。非对称 DMA 缓冲、双向 `mixChannels` 和 100 us 低 CPU 轮询合入后达到 50.18 FPS，相对提升 2.48×（+147.79%），并降低 3.78 个百分点单核 CPU。

分阶段诊断表明，原 RGB32 打包为 28.06 ms/帧，最终降至约 1.69 ms；低字节掩码提取由 5.14 ms 降至约 1.15 ms。DMA 硬件等待约 1.39 ms。最终最大瓶颈是双方共用的 PS 形态学后处理，约 12.17 ms/帧，继续显著加速需要把更多后处理迁移到 PL，而不是继续微调 DMA。

## 6. 实时功能回归

- OpenCV 纯软件摄像头演示：300 帧，约 17.01 FPS，画框与报警状态正常。
- 优化 PL 摄像头演示：约 3 分钟持续运行稳定，17.1±0.1 FPS；实时画面、目标框、报警、G1 蜂鸣器联动和中断资源释放均正常，未出现 DMA 错误或卡死。
- 两个演示 FPS 都包含 USB 摄像头、JPEG 编码和 Jupyter 刷新，不能替代上表的无显示正式吞吐数据。

## 7. 结论

优化没有改变既定接口或检测语义，HLS/Vivado 实现显著减少资源，板端 PS/PL 联合优化后相对纯 OpenCV 获得稳定但有限的 1.04× 吞吐提升，同时 CPU 占用略低，五项效果一致性全部通过。答辩时应将主要硬件收益表述为资源减少与功能等价，将端到端速度收益表述为约 3.7%，不要夸大。
